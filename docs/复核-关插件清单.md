# 复核：关 6 插件清单 × codemode 遮蔽面（native + code_run）

> 票 03-lean-layer（taskId=t3）产物 · 约束台账 v1 验收项 1
> 口径：上游 flash-presets 0.3.2 lean v3 关闭清单；本包遮蔽面 = vendored codemode 0.3.x（票 04）。
> 复核问题（约束台账第 2 条）：六件 disabled 与 codemode 遮蔽面是否重复 / 冲突。

## 结论（先说结果）

**六件全部与 codemode 遮蔽面互补、零重复、零冲突；本包逐件保留 flash 的关闭口径。**
机制上两者正交：

- **关插件（disabled）在注册表加载层移除**：插件不加载，其工具定义根本不注册——不进系统提示，
  code_run 也发现不到、调用不到（上游四机制文档 L130-135：「disabled: true 的插件不加载，工具
  定义不进系统提示」）。
- **codemode 遮蔽在呈现层移除**：注册表从未改动，被遮蔽的工具仍在其中；executor.describe()
  就是请求面（= 标准工具 + code_run），被遮工具程序内部经 code_run 仍可完整调用
  （codemode docs/internals.md L11-25）。

叠加后的净效果：

| 层 | 工具 | 请求面 | code_run 程序内 |
|---|---|---|---|
| 预设活跃行（含六件以外的全部） | 标准工具 | 原生可见 | 可调 |
| MCP / profile bundle / agent 层 | 被遮层 | 剥掉 | 经 code_tools_* 发现后可调 |
| 六件 disabled | 被关层 | 不存在 | 不存在 |

补充一个关键点：**遮蔽替代不了关插件**。codemode 的归属判定把「预设视图内注册的工具」保持
原生（internals L38-47），所以预设自带的工具若不关，schema 照样进请求面付税；关闭是遮蔽之外
唯一能同时从请求面与程序面移除的手段。反过来，关插件也替代不了遮蔽（MCP/profile 层工具
不归本预设管，只能靠遮蔽收口）。

## 六件逐项复核

### 1. tool-subagent-codex（subagent_codex，调 Codex CLI 子代理）

- 上游出处：flash-lean-ptc-v3.patch.yml L155-161（delegation 组内 disabled: true，config
  provider: codex / toolName: subagent_codex / maxDepth: provider-managed）。
- 若不关（本包 native+code_run 面下）：预设作用域行 → codemode 判「预设所有」保持原生 →
  subagent_codex 的 schema 进请求面付税（每个工具定义几百到一千多 token，四机制文档 L132-134）。
- 关掉的净效果：不注册 → 请求面与 code_run 都不可达；省一份固定 schema 税。
- **复核结论：互补不冲突，保留关闭。** 能力代价：失去 Codex 子代理（能力缺失边界与 flash
  相同，四机制文档 L137-140「它是能力和成本的交换」）。

### 2. tool-subagent-claude-code（subagent_claude_code，调 Claude Code 子代理）

- 上游出处：flash-lean-ptc-v3.patch.yml L162-168（同组 disabled: true，provider: claude-code）。
- 分析与第 1 件完全同构（同为预设作用域子代理行）。
- **复核结论：互补不冲突，保留关闭。** 能力代价：失去 Claude Code 子代理。

### 3. workflow-ptc（@deepseek-ai/dsh-workflow-ptc，PTC 版工作流引擎）

- 上游出处：flash-lean-ptc-v3.patch.yml L169-173（disabled: true，config provider: spawn）。
- 关键对照：**codemode 自己的预设反而启用它**（codemode/cordis.patch.yml L124-127 无
  disabled）——说明在 native+code_run 面下工作流引擎与遮蔽层可以共存，关闭是 lean 省
  schema 的选择，不是兼容性冲突。
- 与常驻 PTC 无重叠（易混点澄清）：ptc-runtime 是 run_code/code_run 的**执行模式配置行**
  （executionMode: persistent-in-memory，flash cordis.patch.yml L376-378；本包该行归票 04），
  workflow-ptc 是**工作流引擎插件**。上游同时保留 ptc-runtime 配置并关闭 workflow-ptc，
  两件事互不影响。
- **复核结论：互补不冲突，保留关闭。** 若未来需要 workflow 编排，去掉该行 disabled 即恢复，
  遮蔽层无需任何改动。

### 4. tool-workflow（工作流编排工具组）

- 上游出处：flash-lean-ptc-v3.patch.yml L174-176（disabled: true，无 config）。
- 对照：codemode 预设同样启用它（cordis.patch.yml L128-129）。
- **复核结论：互补不冲突，保留关闭。** 与第 3 件同组同理由；恢复方式相同。

### 5. tool-ralph（ralph 循环执行工具）

- 上游出处：flash-lean-ptc-v3.patch.yml L177-182（disabled: true，config subagentProvider:
  spawn / maxRounds: 64）。codemode 预设无此行。
- 与 code_run 的功能重叠辨析：ralph 是 fresh-agent 多轮循环（每轮新代理、共享工作区），
  code_run 是单程序内的批量子调用（maxParallelSubCalls: 10）——两者都服务「批量执行」，
  机制不同，不构成遮蔽层冲突。
- **复核结论：互补不冲突，保留关闭。** 省 schema，且与本包「程序化批量由 run_code/code_run
  承担」的定位一致。

### 6. tool-plugin-manager（插件市场/管理工具）

- 上游出处：flash-lean-ptc-v3.patch.yml L200-202（预设顶层 disabled: true，恒关）。
- 对照：codemode **条件关**（disabled: !!js "!ctx.get('profileContext')"，cordis.patch.yml
  L143-145），另恒关 tool-plugin-market（L146-148）。
- **复核结论：互补不冲突，本包保留恒关（比 codemode 的条件关更保守）。** 理由：会话内装卸
  插件会改变 bundle 完整性，与计划的风险条款（头号风险=误挂，回滚=整卡移除 + config 双保险）
  冲突；装卸需求走 profile 层操作（dsh plugin add/remove），不依赖会话内工具。
